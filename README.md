# Зоряний клас — пакет документації для розробки

Веб-застосунок для класного керівника: учні отримують **зірки ✦** за оцінки 7–12, підтверджені підписом у щоденнику, і міняють їх на смаколики та привілеї. Облік ведеться псевдонімно (UUID + вигаданий псевдонім), без жодних персональних даних. Вчитель працює через сканер QR, учень бачить баланс на телефоні в реальному часі.

Цей пакет складений так, щоб ШІ-агент (Antigravity) міг прочитати його, скласти план і побудувати систему. Мова документації українська, ідентифікатори в коді англійські.

## Рішення власника (журнал рішень)

| № | Рішення | Деталі |
|---|---|---|
| D1 | Валюта: **зірки ✦** | назва й символ редагуються в налаштуваннях; в інтерфейсі SVG-іконка, у тексті для друку символ ✦ |
| D2 | Зірки = оцінка − 6 для оцінок 7–12 | оцінки ≤ 6 не вносяться |
| D3 | Прайс-лист: карамель 7 ✦, желейка 12 ✦, **тарталетка 17 ✦** | тарталетка зменшена з 40 до 17 (бюджетні наслідки в `02-economy.md`) |
| D4 | Ліміт тарталетки: 1 на учня раз на 30 днів | параметр `cooldownDays`; змінюється в адмінпанелі |
| D5 | Процес зарахування: **учень приходить зі щоденником → вчитель сканує його QR → відмічає отримані оцінки → зірки нараховуються автоматично → вчитель розписується** | учень оцінок не вносить і в базу не пише |
| D6 | Предмет при зарахуванні **не вказується** | швидкість важливіша; захист від повторів дає підпис у щоденнику |
| D7 | Усі учні мають телефони, телефони дозволені | основний канал: застосунок учня (PWA); друкована картка лишається запасним |
| D8 | QR двох видів: `P` (профіль) і `R` (замовлення) | протокол у `06-qr-protocol.md` |
| D9 | Скасування лише **останньої** операції (10 с із панелі, пізніше з журналу), старіші помилки виправляє коригування | просто й безпечно |
| D10 | Стек: HTML + CSS + JS (ES-модулі, без фреймворків і збірки), GitHub Pages, Firebase Spark (Firestore + Auth) | без Cloud Functions і Cloud Storage |
| D11 | Профіль без персональних даних: UUID + псевдонім | таблиця «UUID ↔ дитина» у Firebase не зберігається |
| D12 | «Герой» (аватар і речі) **відкладено** | специфікація збережена в `12-backlog-hero.md` |
| D13 | Погодження з директором не потрібне (за словами власника) | інформування батьків усе одно рекомендоване (див. `05-security-privacy.md`) |

## Припущення і відкриті питання

| № | Питання | Стан |
|---|---|---|
| A1 | Кількість штук на кг: карамель ≈ 180, желейка ≈ 140 | **орієнтовні** значення; уточнити зважуванням пізніше. Розрахунки залежать від них, тому вони лежать у конфігурації (`unitCost`) |
| A2 | Розподіл оцінок у класі | припущення в `02-economy.md`; реальні дані покаже бюджетний модуль |
| A3 | Регіон Firestore | вибрати при створенні проєкту (змінити потім не можна); рекомендація: європейський |
| A4 | Спосіб входу вчителя (email+пароль чи Google) | вирішити при налаштуванні Firebase (T0.3) |
| A5 | Назва репозиторію і адреса GitHub Pages | вирішити при створенні (T0.2) |
| A6 | Текст повідомлення батькам | підготувати перед запуском |

## Глосарій

| Термін | Значення |
|---|---|
| Зірки (✦) | єдина валюта; витрачається на нагороди |
| Профіль | запис учня: псевдонім, баланс, статистика; ідентифікатор UUID v4 |
| Псевдонім | вигадана назва на кшталт «Лис-07» |
| Картка | друкований аркуш з QR профілю (запасний канал) |
| Панель учня | екран вчителя після скану QR: зарахування оцінок і видача нагород |
| Зарахування (credit) | подія нарахування ✦ за вибрані оцінки |
| Списання (redeem) | подія обміну ✦ на нагороду |
| Журнал (ledger) | незмінний список подій профілю |
| Конфігурація | усі параметри економіки одним документом `config/published` |
| Скасування (undo) | відкат останньої операції зі збереженого знімка |
| Опорна позиція | товар (карамель), відносно якого рахуються вартість зірки й рекомендовані ціни |

## Як передати агенту

1. Створіть репозиторій і покладіть у корінь `AGENTS.md` та `README.md`, а папку `docs/` поруч.
2. Відкрийте репозиторій в Antigravity. За вторинними джерелами, Antigravity читає `AGENTS.md` у корені (підтримка з v1.20.3), а в новіших версіях робочі правила також бувають у `.agents/rules/` (сумісно з `.agent/rules/`). Офіційної документації про пріоритет `AGENTS.md` і `GEMINI.md` я не знайшов, тому тримайте правила в одному файлі й без суперечностей. Якщо ваша версія не підхоплює `AGENTS.md`, створіть робоче правило, що посилається на цей файл.
3. Перший запит агенту (скопіюйте):

> Прочитай `AGENTS.md` і всі файли в `docs/` у порядку з `README.md`. Код поки не пиши. Створи файл `PLAN.md` з розділами: (1) твоє розуміння системи в 10 рядках; (2) суперечності або прогалини в документації; (3) уточнювальні питання власнику (лише ті, що блокують роботу); (4) план за віхами M0–M9 із переліком файлів, які створюватимуться; (5) ризики. Потім зупинись і чекай мого підтвердження.

4. Після підтвердження плану працюйте за `docs/11-implementation-plan.md` віха за віхою; після кожної віхи вимагайте запуску тестів і короткого звіту.
