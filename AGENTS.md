# AGENTS.md — правила для агента

## Проєкт

«Зоряний клас» — веб-застосунок для класного керівника 6-го класу (17 учнів): учні заробляють зірки ✦ за оцінки, підтверджені підписом у щоденнику, і обмінюють їх на смаколики та привілеї. Облік псевдонімний, без персональних даних. Повний опис: `README.md` і `docs/`.

## Мова

- Інтерфейс, повідомлення про помилки, тексти для користувачів: **українська**.
- Ідентифікатори в коді, назви файлів, коміти: **англійська**. Коментарі: українська або англійська, але послідовно.
- Відмінювання «зірка/зірки/зірок» через `plural()` (див. `docs/08-ui-ux.md`); ніколи не склеюйте «5 зірка».

## Жорсткі обмеження (MUST / MUST NOT)

1. **Стек:** HTML + CSS + JavaScript (ES-модулі). Жодних фреймворків (React, Vue тощо), жодного бандлера чи транспайлера для коду застосунку. `package.json` лише для тестів і службових скриптів (devDependencies).
2. **Хостинг і бекенд:** GitHub Pages (статика) + Firebase **Spark**: Firestore і Auth. **Не використовувати** Cloud Functions, Cloud Storage, Realtime Database та інші функції, що потребують плану Blaze.
3. **Персональні дані:** **заборонено** зберігати чи логувати імена, email учнів, телефони, фото, назву класу чи школи, вільний текст. Єдині ідентифікатори учня: UUID v4 і вигаданий псевдонім.
4. **Мережа:** єдині зовнішні запити — до Firebase. Версію Firebase SDK зафіксуйте (імпорт зі `gstatic` за точною версією або локальна копія). **Жодної** аналітики, зовнішніх шрифтів, CDN для інших бібліотек. Бібліотеки `jsQR` і `qrcode-generator` лежать локально в `vendor/` (перевірте ліцензії та додайте файл `vendor/LICENSES.md`).
5. **Учні не пишуть у Firestore.** Усі записи робить вчитель (автентифікований). Додавати запис з боку учня можна лише за окремим рішенням власника.
6. **Жодних зашитих чисел економіки** (ціни, пороги, ліміти) у коді: усе береться з `config/published`. Винятки: тестові фікстури та seed-файл.
7. **Рушій чистий:** `src/engine/*` без введення-виведення, без `Date.now()`, без доступу до DOM/Firebase; час передається параметром `nowMs`.
8. **Усі операції зі зміною балансу** (зарахування, списання, скасування, коригування, ручні квести) виконуються лише через `src/data/tx.js` у `runTransaction`, з ідемпотентним `opId` (див. `docs/04-data-model.md`).
9. **Часовий пояс:** `Europe/Kyiv` для місяців, днів і «сьогодні» (див. `docs/07-engine-spec.md`).
10. **Доступність і мобільність:** mobile-first, цілі дотику ≥ 48 px, контраст ≥ 4,5:1, не покладатися лише на колір (див. `docs/08-ui-ux.md`).
11. **Секрети:** у репозиторії немає жодних ключів, окрім публічної веб-конфігурації Firebase (вона не секретна, захист у Rules). Ніколи не комітьте `.env`, ключі сервісних облікових записів, таблицю «UUID ↔ дитина».

## Архітектурні правила

- Шари: `engine` (чиста логіка) → `data` (Firebase, транзакції) → `ui` (відображення). Залежності лише в цей бік; `ui` не містить бізнес-логіки.
- Одна функція рушія і для попереднього розрахунку в UI, і для реального запису (без дублювання логіки).
- Конфігурація читається одним документом `config/published` і кешується; зміни підхоплюються через `onSnapshot`.
- Помилки показуються українською, зрозуміло для дитини (учень) і конкретно (вчитель). Технічні подробиці лише в консолі.

## Робочий процес

1. **Спочатку план.** Прочитайте всі документи, створіть `PLAN.md` (формат у `README.md`) і чекайте підтвердження власника. Не пишіть код до підтвердження.
2. Працюйте **за віхами** з `docs/11-implementation-plan.md` у вказаному порядку. Рушій і Rules пишіть **з тестами першими** (`docs/07-engine-spec.md` містить таблицю тест-кейсів).
3. Після кожної віхи: запустіть тести, коротко звітуйте (що зроблено, що не зроблено, відхилення від документів), оновіть документацію, якщо щось змінилося.
4. Якщо документи суперечать одне одному, зупиніться й спитайте власника; не вгадуйте. Якщо потрібне рішення, що змінює економіку чи приватність, спитайте обов'язково.
5. Малі коміти за правилом Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`).
6. Не розширюйте обсяг: функції з `docs/12-backlog-hero.md` та все, що позначено «пізніше», не реалізуйте.

## Команди

| Команда | Дія |
|---|---|
| `npm test` | `node --test tests/` (рушій, протокол QR, допоміжні функції) |
| `npm run test:rules` | тести Security Rules на емуляторі Firebase |
| `npm run serve` | локальний статичний сервер (камера працює на `localhost`) |
| `npm run seed` | завантаження початкової конфігурації в емулятор |

Назви скриптів зафіксуйте в `package.json` на етапі M0.

## Стиль коду

- ES-модулі, `const`/`let`, без глобальних змінних, без `eval`.
- JSDoc-типи для публічних функцій і структур (`docs/04-data-model.md` задає форми даних).
- Функції малі, імена описові. Без прихованої магії: числа з конфігурації, а не «магічні».
- Жодного `innerHTML` з даними користувача; для тексту `textContent` (захист від XSS, навіть якщо псевдоніми контрольовані).
- Усе, що показується користувачеві, береться з `src/i18n/uk.js`.

## Definition of Done (для кожного завдання)

- Виконані критерії приймання завдання з `docs/11-implementation-plan.md`.
- Є автоматичні тести для логіки; ручна перевірка для UI описана в звіті.
- Немає порушень розділу «Жорсткі обмеження» (перевірити переліком вище).
- Немає `console.error` у штатних сценаріях; помилки мережі показуються користувачеві.
- Оновлено документацію, якщо поведінка відрізняється від неї.

## Коли питати власника

- Зміна цін, лімітів, формул, складу квестів.
- Будь-що, що додає збереження нових даних про учнів.
- Розгортання Security Rules у продакшн Firebase (спершу емулятор, потім підтвердження).
- Вибір регіону Firebase, способу входу вчителя, назви репозиторію.
- Додавання нових залежностей (особливо у браузерний код).

## Заборонені дії

- Додавати аналітику, трекери, зовнішні віджети.
- Зберігати або показувати реальні імена в базі чи в загальнодоступних файлах.
- Видаляти записи журналу або змінювати їх після створення.
- Обходити Rules (наприклад, відкривати запис «для зручності»).
- Змінювати числа економіки в коді замість конфігурації.
