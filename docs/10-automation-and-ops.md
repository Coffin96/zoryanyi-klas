# 10. Автоматизації та експлуатація

## 1. Принцип відбору автоматизацій

Автоматизуємо все, що **не підміняє рішення вчителя** (звірка зі щоденником лишається за ним) і **не потребує сервера** (Spark не має планувальника). Тому «автоматизація» означає обчислення й дії **у момент відкриття застосунку або дотику**, а не фонові задачі.

## 2. Перелік автоматизацій

### Для учня

| Автоматизація | Ефект |
|---|---|
| Запам'ятовування профілю на пристрої | один раз відкрив картку, далі застосунок відкривається одразу |
| Живе оновлення й квитанція | після дії вчителя на телефоні з'являється «+8 ✦» або «Отримано 🍬 −7 ✦» |
| «Що можу взяти» і «ще N ✦» | рахується автоматично з балансу, лімітів, запасу, cooldown |
| Рівні | автоматичний розрахунок і смуга прогресу |
| Відлік до кінця року | показується за 14 днів до `yearEnd` |
| Позначка «Нове» | при новинах, нових позиціях і квестах |
| PWA | встановлення на головний екран, офлайн-оболонка |

### Для вчителя

| Автоматизація | Ефект |
|---|---|
| Сканер → панель | один скан відкриває все потрібне; потоковий режим для черги |
| Попередній розрахунок | +✦ і спрацювання квестів видно до «Зарахувати» |
| Автоквести | «Зростання», «Активний тиждень» нараховуються з урахуванням `perMonth` і `questMonthlyCap` |
| Списання одним дотиком + скасування | баланс, ліміти, запас, журнал в одній транзакції |
| Квитанція учневі | автоматична через `onSnapshot` |
| Прогноз потреби | верхня межа смаколиків на день видачі |
| Бюджет і поріг | автоматичний розрахунок вартості зірки; попередження при перевищенні `budgetAlertUah` |
| Рекомендовані ціни, перевірка «перекосу» | при кожній зміні каталогу |
| Масові дії | створення профілів з друком карток, «Внесок» для кількох учнів, множник цін |
| Нагадування | експорт раз на тиждень, перевірка цілісності раз на місяць (при відкритті панелі) |
| Завершення року | попередження, режим «ярмарку», обнулення залишків із попереднім переглядом |
| Журнал і аудит | ведуться самі |

### Між учнем і вчителем

| Автоматизація | Ефект |
|---|---|
| Ідемпотентність за `opId` | повторне натискання чи повторний скан нічого не дублюють |
| Реальний час | зміна у вчителя миттєво видна учневі |
| Єдиний протокол QR | один сканер обробляє картки й замовлення |
| Узгодження конфігурації | учень завантажує один документ `config/published`, кешує й автоматично підхоплює зміни цін |

## 3. Обмеження

- Фонових задач немає: перевірки, відліки, нагадування виконуються при відкритті застосунку.
- Транзакції балансу потребують інтернету (див. `03-architecture.md §7`).
- Для справжнього розкладу (автоматичні резервні копії, нічні перевірки) можливі пізніше: Cloud Functions (потребують плану Blaze) або заплановані задачі GitHub Actions із ключем Admin SDK у секретах (обережно: репозиторій публічний, резервні копії лише в приватне сховище).

## 4. Відхилені автоматизації

| Ідея | Причина |
|---|---|
| Автозарахування без підпису вчителя | ламає довіру до оцінок і сенс процесу |
| Автоімпорт оцінок з електронного журналу | немає інтеграції; джерело істини це підпис у щоденнику |
| Push-сповіщення | потребують сервера й токенів пристроїв; зайвий розголос приватності |
| Випадкові бонуси | логіка лутбокса, непрозорість для дітей |
| Публічні рейтинги | порівняння дітей, ризик стигматизації |

## 5. Резервні копії

- Експорт JSON раз на тиждень; зберігати поза Firebase (локальний диск, особиста хмара), **не в публічному репозиторії**.
- Перед міграцією, імпортом або масовими змінами автоматичний експорт.
- Відновлення: «Дані → Імпорт» → перевірка відмінностей → підтвердження.
- Раз на місяць: тест відновлення на емуляторі або в окремому тестовому проєкті.

## 6. Кінець навчального року

| Коли | Дія |
|---|---|
| За 14 днів до `yearEnd` | у учнів відлік; у вчителя нагадування |
| Останній тиждень | режим «ярмарку»: підсвічено учнів із залишком, збільшено ліміти видач за потреби (ручна зміна конфігурації) |
| День `yearEnd` | експорт JSON → попередній перегляд списку залишків → «Обнулити» (записи `adjust` з причиною `year-end` або новий сезон) |
| Після | архівація профілів учнів, які залишили клас; перевипуск карток для нового класу за потреби |

## 7. Інциденти й типові дії

| Ситуація | Дії |
|---|---|
| Помилково зараховано | «Скасувати» (10 с або з журналу, якщо це остання операція); інакше «Коригування» з причиною |
| Помилково видано | те саме; запас відновлюється скасуванням |
| Учень загубив картку/телефон | «Перевипустити посилання» → нова картка; старе посилання перестає працювати |
| Витік посилання | перевипуск; перевірка журналу на підозрілі події |
| Не працює сканер | вибір учня зі списку; перевірка дозволу на камеру; запасний декодер `jsQR` |
| Забули пароль вчителя | відновлення через Firebase Auth; резервний адміністратор |
| Перевищено квоту Spark | сервіс обмежується, а не списує кошти; зменшити читання (кеш), дочекатися нового дня |
| Розбіжність балансу з журналом | «Перевірка цілісності» → «Перерахувати з журналу» після підтвердження |
| Бюджет перевищено | змінити `cooldownDays`, ціну тарталетки або `questMonthlyCap` у чернетці → публікація |

## 8. Моніторинг

- Консоль Firebase: використання читань/записів, помилки Rules.
- Панель вчителя: попередження про бюджет, резервну копію, цілісність.
- Після запуску першого місяця: порівняти прогноз бюджету з фактом і підкрутити важелі.
